## Decided

- Sitemap is needed so the research agent has site navigation without having to crawl the site page by page.
- Payment Method + Deposit amount (min/max) will be extracted from screenshots of the Deposit tab's cashier iframe (`pf-west1.slotoro.cc/player/profile-cashier/...`, cross-origin, not queryable via `document.contentDocument`) per method, one screenshot per method — collection loop: select method tile → screenshot → "Choose another method" → repeat until all methods covered. Chosen because payment method icons in the tile grid carry no accessible name/alt text, so the method name is only readable from the rendered screenshot (e.g. "Payment method: Visa" label shown after selection), not from the a11y snapshot.
- Deposit-method loop tooling: `mcp__playwright__browser_snapshot` called with a `filename` (writes to disk instead of returning inline) then `grep` on that file for `min:` and `Choose another method` lines to get element refs — never read the raw snapshot inline. Reason: one unfiltered `browser_snapshot()` call on this page measured 116,438 chars / 2,361 lines (~29k tokens) and was rejected outright for exceeding the per-call token cap. The filename+grep pattern cut each lookup to the ~15 lines actually needed (~150-300 tokens). Per-method iteration = 1 `browser_click` (select tile, ~100 tokens) + 1 `browser_take_screenshot` (~100 tokens) + 1 `Read` of the resulting PNG (~1,200-1,600 tokens, fixed image cost) + 1 `browser_click` (Choose another method) + 1 grep (~150-300 tokens) ≈ 2,000-2,500 tokens/method, vs. ~29k tokens if a full snapshot were read per step — roughly a 10x reduction. Applies to any future scripted UI-crawl of this type (deposit/withdraw method tables, bonus grids, etc.) on this or similar cashier iframes.
- ~~Withdraw tab's payment-method widget is the same cross-origin cashier iframe as Deposit~~ — corrected below: Withdraw does NOT need the per-method iframe loop.
- Payment info flow completion criterion: done when, per method, the available Payment Method name + Deposit amount (min and max, whichever the site exposes) have been collected — no further per-method drill-down once name+min/max are captured, even if max is unavailable (site may only expose min, as here).
- Player bonus research exclusion criterion: bonuses with a fixed validity window (a "Dates: X - Y" or "Ends in: N days" field, e.g. tournament/prize-pool promos) are out of scope and not collected — only bonuses without a time-bound end date are captured. ## Failed

- Computed grid-position → element-ref offsets by hand (base ref + 4×position) to click payment tiles without re-reading the full snapshot each time — arithmetic slip on the BNB step (used the Dogecoin offset again) re-selected Dogecoin instead of BNB. Root cause: manual offset arithmetic across a 16-item list has no self-check; caught only by screenshotting and visually confirming the selected method name each time. Verifying every click's result via screenshot, not just trusting the computed ref, is what caught it.
- Took a `fullPage: true` screenshot of the account bonus-program modal (`#!/player/bonus-program`) and got a 41,224px-tall image with the modal duplicated ~3 times. Root cause: the modal is a fixed-position overlay on top of a `body.overflow-hidden` page, so `fullPage` screenshotting (which scrolls and stitches) re-captures the fixed element at every scroll step instead of scrolling past it. Fix: use a plain viewport screenshot for fixed/sticky overlays, not `fullPage`; to reveal content further down inside the overlay, scroll its own internal `overflow-y-scroll` container directly via `element.scrollTop += N` (found by querying for elements where `scrollHeight > clientHeight`) — `window.scrollBy` has no effect since the body itself doesn't scroll.
